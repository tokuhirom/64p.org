*GC
----
最初は Arc (参照カウント) だけで動いてた
→ 循環参照がリークする
----
Raku だと循環参照はわりと普通に出てくる
- 再帰するクロージャ
- 親子関係のオブジェクト
- Promise / Supply
----
GC がないインタープリタは、誰も使ってくれない
----
選んだのは
非移動 (non-moving) の参照カウント + cycle collector
<!-- ADR-0001 (2026-06-27) -->
----
なぜ？
→ Rust の Value がそこら中のスタックに生で転がってる
→ moving GC にすると、それを全部追いかけないといけない
→ 動かさないなら JIT もシンプルにできる
----
7月5日 GC デフォルト on

*JIT
----
バックエンドは Cranelift
----
- LLVM は重い (ビルドも起動も)
- 手書きのアセンブラは CPU ごとにメンテが要る
- Cranelift は pure Rust で、wasmtime での実績もある
----
method JIT にする
→ tracing JIT はやらない
→ OSR も最初はやらない
----
GC → NaN-boxing → JIT
この順番は最初に決めておいた
----
非移動 GC にしてあるので
JIT 側はスタックマップも write barrier もいらない
----
J1 から J5 まで 2日 で終わる
(7月12日〜13日)

何が起きるか
----
ADR の番号がかぶる
→ 「最大番号 + 1」で採番してたら、並列 PR が同じ番号を取る
→ 6 回かぶった
→ ADR 番号 = issue 番号 にした
----
CI が詰まる
→ GitHub Actions の同時実行 20 ジョブの枠を食い尽くす
→ PR が 5〜15 分待ち
→ 重いテストは PR から外して、main で 1 時間ごとに回す
----
main が赤くなる
→ 約20 の PR がそれぞれ勝手に直そうとする
→ runner が埋まって、また壊れる
→ 「main is red」issue を 1 個立てて、直すのは 1 人だけ、にした
----
flaky test
→ 調べたら、だいたい普通のバグだった
→ テストのポート番号がかぶってた、とか
----
`while pgrep -f "make lint"`
→ 自分自身のシェルにマッチして永遠に終わらない
----
`pkill -f "make test"`
→ 自分のシェルを殺す
----
(´・ω・`)

----
roast や doc を submodule にしている
→ AI が mutsu の issue を本家のリポジトリに立てる
