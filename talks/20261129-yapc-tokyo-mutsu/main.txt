<div class="en">The parser</div>

<div class="en">Next, we're changing how we represent the parser's output<br>Moving the AST it produces to RakuAST<br>RakuAST is an AST, not a parser</div>

*GC
----
最初は Arc (参照カウント) だけで動いてた
→ 循環参照がリークする
<div class="en">At first it was just Arc (reference counting)<br>Cycles leaked</div>
----
Raku だと循環参照はわりと普通に出てくる
- 再帰するクロージャ
- 親子関係のオブジェクト
- Promise / Supply
<div class="en">Cycles are common in Raku:<br>recursive closures / parent-child objects / Promise, Supply</div>
----
GC がないインタープリタは、誰も使ってくれない
<div class="en">Nobody will use an interpreter that leaks cycles</div>
----
選んだのは
非移動 (non-moving) の参照カウント + cycle collector
<!-- ADR-0001 (2026-06-27) -->
<div class="en">The choice:<br>non-moving reference counting + a cycle collector</div>
----
なぜ？
→ Rust の Value がそこら中のスタックに生で転がってる
→ moving GC にすると、それを全部追いかけないといけない
→ 動かさないなら JIT もシンプルにできる
<div class="en">Why?<br>Rust Values live raw on stacks everywhere<br>A moving GC would have to track all of them<br>Non-moving keeps the JIT simple too</div>
----
7月5日 GC デフォルト on
<div class="en">July 5: GC on by default</div>

*JIT
----
バックエンドは Cranelift
<div class="en">Backend: Cranelift</div>
----
- LLVM は重い (ビルドも起動も)
- 手書きのアセンブラは CPU ごとにメンテが要る
- Cranelift は pure Rust で、wasmtime での実績もある
<div class="en">LLVM is heavy (build and startup) / hand-written assembly needs per-CPU maintenance / Cranelift is pure Rust and proven in wasmtime</div>
----
よく呼ばれる関数・メソッドを丸ごとネイティブコードにする
→ 実行中のループから JIT へ途中で乗り換える仕組みは後回し
<!-- tracing JIT は実行経路を記録してコンパイルする方式。OSR は実行中のループから JIT コードへ切り替える仕組み -->
<div class="en">Compile hot functions and methods as a whole<br>Defer switching a running loop into JIT code</div>
----
GC → NaN-boxing → JIT
この順番は最初に決めておいた
<div class="en">GC → NaN-boxing → JIT<br>This order was decided up front</div>
----
GC を「参照カウント + 非移動 + 世代別じゃない」にしてあるので
→ JIT はスタックマップも write barrier もいらない
→ 参照カウントの増減さえ正しく出せばいい
<!-- ADR-0004 §2.4, ADR-0001 -->
<div class="en">Because the GC is refcounting + non-moving + non-generational,<br>the JIT needs no stack maps and no write barriers<br>It just has to emit the refcount increments and decrements correctly</div>

何が起きるか

----
ADR の番号がかぶる
→ 「最大番号 + 1」で採番してたら、並列 PR が同じ番号を取る
→ 6 回かぶった
→ ADR 番号 = issue 番号 にした
<div class="en">ADR numbers collide<br>"max + 1" numbering made parallel PRs take the same number<br>6 collisions<br>Now ADR number = issue number</div>
----
CI が詰まる
→ GitHub Actions の同時実行 20 ジョブの枠を食い尽くす
→ PR が 5〜15 分待ち
→ 重いテストは PR から外して、main で 1 時間ごとに回す
<div class="en">CI gets clogged<br>Using up GitHub Actions' 20 concurrent jobs<br>PRs wait 5-15 minutes<br>Heavy tests moved off PRs to hourly runs on main</div>
----
main が赤くなる
→ 約20 の PR がそれぞれ勝手に直そうとする
→ runner が埋まって、また壊れる
→ 「main is red」issue を 1 個立てて、直すのは 1 人だけ、にした
<div class="en">main goes red<br>~20 PRs each try to fix it on their own<br>runners fill up, it breaks again<br>Now: open one "main is red" issue, and only one agent fixes it</div>
----
頼んでいない upstream の変更を AI が始める
<div class="en">AI started changing upstream projects without being asked</div>
----
mutsu の作業を頼んだだけなのに
→ AI が Roast 本家にバグ報告や PR を勝手に出した
→ そんなことは依頼していない。。
<div class="en">I only asked for work on mutsu<br>AI filed bug reports and PRs against upstream Roast on its own<br>I never asked it to do that</div>

Raku のみなさん、すみませんでした。。
<div class="en">Sorry, Raku folks...</div>
